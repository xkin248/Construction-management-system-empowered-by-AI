## 6. 方法论与审计点

- 训练/验证切分沿用既有 group split：dev seed 42、test seed 2026、valid seed 31337（按清洗标题分组，同一标题不跨切分）。valid_train 248 行、valid 83 行。
- 合成语料 3074 条（train 拆分）；其中 496 条由 valid 标题反向生成，**全部从训练中剔除**，否则等于把留出集内容以复述形式喂回模型。
- 多标签决策在 dev 上网格搜索（C × threshold × margin 共 75 组），取集合完全正确率优先，选定 C=4.0、threshold=0.35、margin=0.25；valid 未参与调参，也没有因为本次口径修正而改动任何超参。
- 多标签的第二标签受「共现约束」限制：只有当 (主标签, 次标签) 是训练集里真实共现过的组合（同一标题被映射到两个工种，支持度 ≥ 5）时才允许加入。无此约束时，纯阈值规则会把 `automobile detailer` 判成 laborer + painting 之类的随机次标签，dev 集合完全正确率反而从 97.1 % 掉到 85 % 左右。
- 8 个变体共享同一次 valid 读取、同一批 valid_train 训练数据、同一套关键词词表；唯一差异是表中列出的训练数据、标签方案、C 与规则链开关。本次重跑补上了 V0 基线、两条 rules=on 的候选行与严格口径，仍未用 valid 结果回改任何训练超参（C / threshold / margin 全部来自 dev）。
- 口径差异（必须明示）：V0 采用登记配置 C=50、规则链开、单标签、决策为 argmax + 低置信跳过；A~F 采用 dev 调优 C=4，A/B/F 为 argmax、C/D/E 为 OvR + threshold/margin + 共现约束，规则链在 A~D 上关闭、E/F 上开启。因此 A 的数值低于 V0 属配置差异，不能解读为「上轮 → 本轮退化」。
- Top-1 两种定义同时给出（第 2 节）：集合口径与上轮上报口径一致、可直接比；严格口径把多标签行排除在分母外，用于回答「单标签任务是否被多标签改造拖累」。

## 7. 口径审计：本次修正暴露的两个隐患

- **覆盖率门限误伤了单标签模型**。上一轮之后新增的 `TRADE_CLASSIFIER_MIN_COVERAGE`（词表覆盖率 < 0.34 且无关键词命中就跳过）是为 One-vs-Rest 的饱和概率写的，但最初没有区分标签模式，于是同一套登记配置在当前代码上只能拿到 89.2 %，与上轮上报的 92.8 % 差 3.6 pt。现在该门限只在 `label_mode == "multi"` 时生效，单标签路径回到历史行为，V0 因此精确复现 92.8 %。这也说明「同一配置、不同代码版本」的对比会悄悄失真，必须像本次一样在当前代码上重跑基线。
- **依赖版本漂移**。首次重跑时虚拟环境里是 scikit-learn 1.9.0 / numpy 2.5.2，而 `requirements.txt` 锁的是 1.5.2 / 1.26.4，加载旧 artefact 会报 `InconsistentVersionWarning`，且同一份代码在不同版本下的数字不可比。已按 requirements 把环境装回 1.5.2 / 1.26.4 后重跑，本报告所有数字都出自该环境。

## 8. 多标签增益为何为负：次标签在 valid 上从未触发的实证

- valid 里只有 **2 行**真多标签，两行都是 `{flooring, tiling}`（`residential carpet installer`、`wall to wall carpet installer`）。该组合在 valid_train 的共现计数为 37（≥ 5），因此 `flooring+tiling` **确实在** allowed_pairs 里——不是共现守卫把次标签挡掉的。

| 文本 | 真值 | 多标签预测 | flooring / tiling 概率（多标签） | flooring / tiling 概率（单标签 B） |
| --- | --- | --- | --- | --- |
| residential carpet installer | ['tiling', 'flooring'] | ['flooring'] | 0.956 / 0.267 | 0.941 / 0.002 |
| wall to wall carpet installer | ['tiling', 'flooring'] | ['flooring'] | 0.980 / 0.199 | 0.916 / 0.001 |

- 上表来自同一次 valid 读取、同一批训练数据：多标签训练把 `tiling` 的 OvR 概率从单标签的 ~0.001 抬到 0.2 ~ 0.27（两个数量级），说明 OvR 方向是对的；但它仍低于 dev 选定的 threshold=0.35（且 margin=0.25 要求次标签概率不低于主标签的 0.25 倍，即约 0.24），于是次标签一次都没被加入。
- 因此所有变体在 valid 上的 `multi-pred` 行数分别是 V0 prev_registered=0, A single_tuned=0, B single_synth=0, C multi_base=0, D multi_synth=0, E multi_synth_rules=0, F single_synth_rules=0——没有一行真的输出两个工种。所以「多标签不如单标签」（A→C：Top-1 91.6 % → 90.4 %、B→D：95.2 % → 92.8 %）**不能**解读为「多标签决策有害」，它实际等于「OvR 主标签精度略低于多类 argmax，且次标签能力在这 2 行上没能生效」。
- 不因为这条发现回调阈值：dev 网格已经在 [0.15, 0.2, 0.25, 0.3, 0.35] 上搜过并选定 0.35，为了在 valid 的 2 行上多拿分而把阈值压到 0.2 以下，等于拿 valid 调参、破坏单次读取约定。要让多标签真正生效，正确路径是在 dev 池上增加双标签样本或对次标签单独做概率校准，而不是在 valid 上掰阈值。
- 归纳：多标签改造在 83 行、2 个双标签行的 valid 上**既不能证实也不能证伪**；报告里所有多标签数字都应按「OvR 概率排序下的主标签表现」来读。
