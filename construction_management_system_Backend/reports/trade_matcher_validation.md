# Trade matcher v2 – supervised classifier + title rules, measured on a third split

Generated by `scripts/eval_trade_validation.py` (LLM fallback hard-disabled, deterministic). All figures below are reproducible from that script.

## 1. What was changed

The keyword layer and the TF-IDF profile matcher are both *bag-of-words similarity* models: a task text is scored against per-trade keyword lists / averaged title centroids. Five failure families are structurally out of reach for that shape of model because the discriminating signal is a head noun or a suffix, not overall similarity:

| family | example | why similarity fails |
| --- | --- | --- |
| painting | `spray painter`, `painter decorator` | shares `wall`, `coat`, `surface` with masonry/tiling; the paint centroid is diluted by hundreds of titles |
| drywall | `drywall hanger`, `taper` | `board`, `panel`, `ceiling` overlap with carpenter / tiling |
| plasterer family | `ornamental plasterer`, `molding plasterer` | the dataset files plasterers under **drywall**, while the rules own the word `plaster` (→ masonry) |
| material handler | `material handler` | `material` sits next to the insulation (hazmat) centroid |
| `* operator` | `soldering machine operator` | `operator` belongs to the equipment rule and dominates the centroid of every machine-trade title |

Three changes:

1. **Supervised classifier** (new): multinomial logistic regression on the row labels themselves - `tfidf(word 1–2 g) + tfidf(char_wb 3–5 g)` → `LogisticRegression(C=50)` - trained on the 518 mapped rows plus the seed vocabulary (repeated ×3). It outputs per-trade probabilities. A keyword hit adds +0.5 probability, so hand-checked domain knowledge still steers the decision but can no longer *own* a trade on its own (`precast concrete ironworker` hits masonry keywords, yet is a welding title). The classifier abstains - falling through to the old skip / LLM-suggestion path - when its top probability is below 0.25 and no keyword fired.
2. **Compound-title rules** (new): five literal patterns for families where the head noun decides and no bag-of-words model can weigh it: `boiler maker|installer|mechanic|setter|fitter|erector` → welding (boilermakers are pressure-vessel fabricators, not HVAC - `boiler operator` is deliberately excluded); `cargo|package|freight|stock|baggage|luggage|material handler` → laborer; `wallpaper*` → painting; `soldering|brazing|sub arc|arc weld|spot weld|seam weld` **+ operator/tender/setter/machine** → welding; `furnace mason` → masonry.
3. **Thirteen vocabulary terms** (new): `solder(ing)`, `brazing`, `boilermaker`, `sub arc`, `arc weld`, `spot weld`, `boiler installer`, `boiler mechanic` (welding); `material handler`, `cargo handler`, `package handler`, `freight handler` (laborer); `wallpaper`, `wallpapering`, `decorator` (painting); `cement patcher`, `furnace mason`, `refractory` (masonry). The pre-round tables are frozen in `scripts/fixtures/trade_keywords_pre_v2.json` so §3's baseline stays reproducible.

> Honesty note: changes 2 and 3 were derived from reading run 1's failures **on the valid split**, so their effect on `valid` is post-hoc by construction. §3 therefore keeps them in a separate column from the pre-registered classifier run, and the honest headline number is the classifier column, not the shipped column.

The old TF-IDF profile matcher is kept as the degraded path: missing artefact, older sklearn, any load error → previous behaviour, never an exception. LLM fallback is untouched (it still fires on low confidence in production; it is disabled here so the numbers describe the deterministic layers).

**Valid split, frozen configuration (run 1, honest): 69.9 % → 77.1 % (+7.2 pp)** on n = 83; Wilson 95 % CI for the after-accuracy 67.0 % – 84.8 % (before 59.3 % – 78.7 %). Skips 5 → 5. Macro per-trade recall 77.5 % → 79.3 %. Exact trade-set match 67.5 % → 75.9 %.

**Same rows with the rules and the new vocabulary (run 2, optimistic): 92.8 %** (+22.9 pp vs before, CI 85.1 % – 96.6 %), skips 2, macro recall 86.5 %. These two components were written *after* reading run 1's failures on `valid`, so this second pass is a post-hoc measurement, not a clean one - the honest number to quote is run 1 (77.1 %), and run 2 should be read as "what the shipped pipeline does on these rows", not "what it will do on new ones".

Sanity check on the frozen baseline: the same snapshot reproduces the previously published dev/test figures unchanged (test 80.7 % vs the 80.7 % reported last round), which confirms the snapshot is the real pre-round vocabulary and not a re-typed approximation.

Paired tests on identical rows (exact McNemar, two-sided):

| comparison | fixed | broken | p-value | note |
| --- | ---: | ---: | ---: | --- |
| dev clf | 0 | 4 | 0.125 | fitted split, for reference only |

> p = 0.070: with n = 83 the gain is directionally clear (+7.2%) but **not significant at the 5 % level**. The defensible claim is "better, on limited evidence". The interval is wide because the split has only 83 rows - recall per trade moves ±10 pp per row.

## 7. Artefacts and cost

| item | value |
| --- | --- |
| classifier artefact | `data/trade_classifier.joblib` (0.51 MB, joblib `compress=3`) |
| features | word 1–2 g (≤ 12 k) + char_wb 3–5 g (≤ 18 k), float32 |
| new dependencies | **none** - scikit-learn / numpy were already required by the profile matcher |
| runtime memory | one short string → one sparse row; the loaded model is a few MB of coefficients, comfortably inside a Render free instance (512 MB) |
| per-request cost | 2 `transform` + 1 `predict_proba` over 16 classes, sub-millisecond for a single row |
| artefact ↔ runtime alignment | requirements pin `scikit-learn==1.5.2` / `numpy==1.26.4`; matcher built with scikit-learn 1.5.2 / numpy 1.26.4; classifier built with scikit-learn 1.5.2 / numpy 1.26.4. both were retrained inside the pinned environment, so the shipped bytes are the bytes that were validated. `app.ai_service` records every load in `MODEL_STATUS` and warns on missing / broken / version-skewed artefacts instead of falling back to keywords silently, and `/health` exposes `models_ok` |
| embedding / torch | **not used** - hundreds of MB of image for a gain that cannot exist on a 518-row label set; the char n-gram block already absorbs the spelling variants an embedding would have covered |

## 8. What is still unsolved, and why

| issue | status | reason |
| --- | --- | --- |
| 518 labelled rows for 16 trades | open | the parquet has 6 539 rows but only 518 map to a construction trade; a 25 % split leaves 1–12 rows per trade, so per-trade recall carries ±10 pp of sampling noise whatever the model |
| labels are O*NET *titles*, tasks are free text | open | supervision teaches occupation names; a site description ("chip old plaster off the bathroom wall before tiling") has no counterpart in training, so measured accuracy is a lower bound for keyword-shaped input and an unknown quantity for long prose |
| trade-set ambiguity (`tiling` vs `flooring`, `masonry` vs `drywall`) | inherent | one dataset category legitimately maps to two trades; scored as "any expected trade counts", the only defensible rule, which caps headline accuracy below a clean 1:1 ceiling |
| multi-label output | open | the classifier is single-label (argmax): rows that truly need two trades return one. Fixing it needs multi-label supervision the dataset does not provide |
| `material handler` vs hazmat | partial | the rule sends bare `* handler` to laborer; `hazardous material handler` still leans insulation through the keyword prior, and the dataset offers no such row to prove either way |
| `* operator` beyond welding | partial | welding-process operators are handled; `bolting machine operator`, `transformer maker` and similar one-off titles remain wrong and are visible in §6 |
| BM / Chinese wording | partial | seed keywords cover both, but neither the titles nor the classifier were trained on real BM/Chinese task text |

## 10. Tests and repository state

`pytest tests -q` is green **in two environments**: **85 passed** in the pinned runtime
(Python 3.11.8 + `scikit-learn 1.5.2` / `numpy 1.26.4` / `joblib 1.4.2`, installed from
`requirements.txt` into a clean venv) and **85 passed** in the developer environment
(`scikit-learn 1.9.0`), which is the one that used to swallow the skew.

| guard | what it locks |
| --- | --- |
| `test_requirements_pin_the_pickle_libraries` | `scikit-learn` / `numpy` / `joblib` stay pinned, otherwise the alignment check below would pass on nothing |
| `test_both_artefacts_load_without_degrading` | both bundles load here, `degraded == []`, and the loaders return real objects rather than `None` |
| `test_artefacts_record_the_pinned_build_versions` | each bundle's `meta` versions equal the pins in `requirements.txt` - compared against the pins, not the locally installed wheels, so the guard also holds for a developer on a newer scikit-learn |
| `test_trainer_writes_build_metadata` / `test_pickle_version_stamp_is_read_as_fallback` | the retraining script stamps versions, and a legacy bundle without `meta` is still read through `_sklearn_version` |
| `test_version_skew_is_flagged_not_swallowed` | a 0.0.1-vs-installed mismatch loads but is marked `version_mismatch` **and** logged |
| `test_missing_artefact_marks_degraded` / `test_broken_artefact_degrades_with_warning` | missing and corrupt bundles are `missing` / `failed`, warn, and still degrade instead of raising |
| `test_startup_self_check_screams_when_degraded` / `test_startup_self_check_is_quiet_when_healthy` | `log_model_status()` (called from `app.main` at boot) logs an **ERROR** when anything is degraded and nothing at ERROR level when healthy |

Alignment evidence, beyond green tests:

* both artefacts were retrained **inside** the pinned venv; the matcher reproduces the previous
  (1.9.0-built) model exactly - its `trade_vectors` difference against the old file has 0 stored
  entries - and the classifier keeps the same vocabulary (1 399 word / 6 699 char features) and
  the same 16 classes;
* prediction parity old vs new classifier: **1 517 / 1 517 identical** on the training strings,
  so aligning the versions changed no decision, it only made the shipped model loadable;
* **measured, not assumed**: loading the previous 1.9.0-built bundles under 1.5.2 does **not**
  raise - joblib returns both objects, scikit-learn emits one `InconsistentVersionWarning` per
  estimator, and a probe on `"wireman for site wiring"` still answered `electrical`. The
  production symptom was therefore not "classifier switched off" but "classifier running on a
  pickle its runtime does not support, with nothing in the logs or `/health` to notice if a
  future scikit-learn change did break it". Both halves are now covered: the committed bytes are
  rebuilt under the pins, and any future load problem is recorded in `MODEL_STATUS`, warned
  about, and reflected in `models_ok`;
* Python patch level differs by one (build 3.11.8 in the local venv, `runtime.txt` pins 3.11.9).
  Pickle compatibility is bound to major.minor, so this is irrelevant; it is stated here rather
  than papered over;
* loading under the pinned venv produces **no** `InconsistentVersionWarning`; the old files
  produced six (TfidfTransformer ×2, TfidfVectorizer ×2, FeatureUnion, LogisticRegression),
  which is exactly the drift this round removes;
* `trade_classifier.joblib` grew 0.31 MB → 0.51 MB - same content, different zlib stream from
  joblib 1.4.2 - and carries an extra `meta` block with `labelled_titles` (542 titles drawn from
  518 labelled rows, 24 rows legitimately map to two trades) and `seed_rows` (975), so "1 517
  samples" can no longer be mistaken for 1 517 supervised examples.

Runtime visibility added in `app/ai_service.py` / `app/main.py`: `MODEL_STATUS` (per-artefact
`state` / `path` / `built_with` / `error`), `runtime_versions()`, `_load_artifact()` (records
`loaded` / `version_mismatch` / `missing` / `failed` / `unavailable`, warning at load time),
`model_status()`, `log_model_status()` (startup self-check) and `/health` fields `models` +
`models_ok`. A silent keyword-only fallback is no longer reachable without a log line and a
`models_ok: false` in the health payload.
